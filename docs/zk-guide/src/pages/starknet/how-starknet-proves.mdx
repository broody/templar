# How Starknet proves

## Cairo: a computer whose traces are proofs

Cairo is a virtual machine with one design goal: **every execution is
provable**. A Cairo program compiles to instructions the VM executes;
the VM's state (program counter, memory, registers) advances step by step,
producing exactly the kind of trace table Part 3.1 described. The Cairo AIR
turns "the VM ran correctly" into per-row equations.

This is why anything written in Cairo — a token transfer, a DeFi swap, a
payment statement — is automatically STARK-provable. There is no separate
"circuit design" step: the *language is the arithmetization*.

## The Starknet flow

1. Users submit transactions; the **sequencer** executes them inside the
   **Starknet OS** — a Cairo program that defines the chain's rules.
2. Thousands of transactions become one giant trace.
3. A proving service (historically SHARP) STARK-proves the batch.
4. The proof goes on-chain (L1 Ethereum) where a small contract verifies it;
   the new state root becomes canonical.

For most Starknet history, all of this was **transparent by necessity**:
the trace contains transaction data that is public anyway (senders,
amounts, contract calls). Witness privacy is worthless when the witness is
the public ledger — which is exactly why the core proving stack (Part 3)
was built with zero zero-knowledge features. Soundness only.

## The native proof-verification path

Starknet itself accepts STARK proofs as first-class transaction payloads.
A proof-carrying transaction specifies a **proof version** (PROOF1, PROOF2)
and carries proof bytes plus **proof facts** — the public inputs the proof
commits to. The gateway/sequencer verifies the STARK *natively* (protocol
level), and the receiving contract learns only the verified facts.

Measured in this repo: a full payment lifecycle's proofs (~232 KB each)
submitted through the official Sepolia gateway, accepted at ~80–95M gas
per spend — with **no in-contract verification cost at all**, because the
sequencer did the verification. For contrast, verifying a SNARK in-contract
(Garaga) costs ~150–270M gas *per proof* on top of everything else. This
asymmetry decided the proof system for user-proven designs (Part 2.3).

Caveats from the same measurements: proof-version acceptance is a rollout
property (the tested RPC's estimator rejected PROOF1 even as the gateway
accepted it), and facts/bindings must be checked contract-side with care —
the proof proves *a* statement; the contract must check it proves *the
intended* one.

The two versions differ in size. PROOF1 verifies Cairo executions whose
largest trace component fits 2^20 rows. PROOF2, added in Starknet v0.14.4,
keeps a small path and adds a **large path** for traces from 2^25 to 2^29
rows (`privacy_recursive_prove_large`). A large proof takes minutes and tens
of GiB to generate, but lifts the size ceiling for server-side work.
Acceptance is again a rollout property: Sepolia runs v0.14.4, whose protocol
constants allow PROOF2, yet the official gateway still rejected a PROOF2
submission on 2026-09-20.

## Where user-held secrets fit — and where they don't

A payment protocol wants the *user* to prove statements over **secrets the
sequencer never receives**: note ownership, membership, nullifier
derivation. Three architectures matter here:

1. **Centralized prover (upstream's deployment)**: the user sends
   everything — per this repo's inspection of upstream's SDK, the proving
   service receives the user's address, private key, and every action in
   plaintext — and the operator's proof wraps the public outputs. The
   posted artifact hides nothing the operator didn't already know.
2. **Full Cairo proving on the client (the accepted baseline)**: the user
   generates the Cairo/virtual-OS privacy proof locally and submits PROOF1.
   This has a demonstrated Sepolia payment path, but the generic VM, OS and
   felt252 machinery make it expensive for ordinary desktops and browsers.
3. **Compact private client proof + server wrapper (the new path)**: the
   user's device proves only the private payment transition in a purpose-built
   M31 AIR. A server verifies that inner proof and proves the public wrapper
   computation as a PROOF2 large proof. The server
   may learn the public transaction intent, but must never receive notes,
   keys, Merkle paths or private amounts.

All three use STARK machinery; they differ in *who is trusted with secrets*,
*where generic Cairo execution happens*, and *who bears the memory bill*.
The third route is explained on the [next page](/starknet/client-proof-wrapping).

## What to carry forward

1. Cairo makes *everything* provable; the OS makes the *chain* provable.
2. Starknet verifies STARK proofs natively — proof-carrying transactions
   are cheap on-chain.
3. Transparency is the default because public-ledger traces need no hiding;
   private-payment traces change that, and Part 5 begins there.
