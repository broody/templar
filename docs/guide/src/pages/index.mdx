# Private value. Public verification.

<p className="guide-lead">Templar is a private token pool on Starknet with push payments to reusable cloaked receiving addresses. Share a cloaked address, receive while offline, and prove spends locally without publishing your private note data.</p>

Templar is based on [StarkWare's starknet-privacy](https://github.com/starkware-libs/starknet-privacy), with its auditor and deposit-screening roles removed and proving moved to the user's device. No central proving operator needs to receive users' secrets. The [trust model](/architecture/privacy#trusted-roles-removed) explains these boundaries and the remaining authority of optional note controllers and pool configuration.

The [Starknet Privacy comparison](/comparison) shows how the two architectures differ in trust, note handling, supported flows, and client responsibilities.

The pool holds ERC20 tokens. A user's private balance is the sum of the unspent **notes** they control. Each note describes some value and a spending condition. The chain stores a cryptographic commitment to the note rather than a private balance indexed by wallet address.

To pay someone, a holder consumes existing notes and creates fresh encrypted notes for the recipient and, when needed, change. A zero-knowledge proof establishes ownership, membership in the pool, and conservation of value. The pool binds the proof to the exact operation and publishes the encrypted outputs atomically. The recipient discovers them later using their wallet keys.

## Four ideas to keep in mind

| Idea | What it means in Templar |
| --- | --- |
| A note is a claim on pooled value | Spending requires its opening and the owner's spending secret. |
| A commitment records creation | A hash binds the note's value and spending conditions into the pool's tree. |
| A nullifier records consumption | A derived public identifier can be used only once, without directly naming the consumed tree leaf. |
| A proof authorizes specific changes | The proof is bound to the pool, chain, public statement, and exact action list. |

These concepts are similar to consuming and creating outputs in a UTXO system. The additional work is proving which hidden inputs are valid without disclosing their openings or their positions in the tree.

## Scope

This guide explains the architecture and its security boundaries. The proving path uses S-two's recursive zero-knowledge privacy pipeline with the PROOF1 format and Starknet's native proof verification. The current reference supports up to four inputs, four outputs, and two withdrawals for one public token. Larger native statements are evaluated separately on the [status page](/status#spend-capacity-pathfinding).

Ordinary and controlled push payments, watch-only balances, seed recovery, recovered-note spends, and withdrawals have been demonstrated through isolated Sepolia deployments. On the compact client-proof path, [open notes](/architecture/open-notes) and [policy notes](/architecture/policy-notes) have been demonstrated locally with real proofs. Production integration, independent review and desktop qualification remain open. The [implementation status](/status) page identifies what is demonstrated and what remains unqualified.
