# Existing wallets

Templar has **one wallet model** (ADR-0027, `docs/adr/0027-one-wallet-model.md`). Every user holds ordinary Templar notes, and the Templar key authorizes every spend inside the client proof. An existing Starknet wallet (Ready, Braavos, Cartridge Controller, or any account) connects to the site only to:
- log in;
- deposit into the pool;
- receive withdrawals;
- pay for the service.

It never authorizes a spend, so any account type works: guardians, multisig and passkey accounts included. Every spend is the same kind of ordinary spend in the same pool, so all users share one anonymity set.

## The Templar key

The Templar key comes from a 24-word backup, the only backup there is. A leaked backup means theft, as with any wallet seed. The external wallet adds no second signature.

At launch the key lives in a vault on its own origin, `vault.templar.money`, embedded in the site. The vault holds the seed, syncs the pool and proves spends. Unlocking, showing the words and confirming each spend open a separate vault window. The vault is specified but not built yet. A Chrome extension wallet may follow later, with one 24-word seed for both its account and its Templar key.

## A spend

  { title: 'Prove', detail: 'The vault plans the spend and proves it on the device, in about 6 seconds. Keys, amounts and recipients stay there.' },
  { title: 'Wrap', detail: 'The prover server runs its statement account in the virtual OS and returns the large proof. It learns nothing about the spender.' },
  { title: 'Relay', detail: 'The service’s relayer submits the transaction from its own account.' },
]} caption="The external wallet takes no part in a spend. It only funds deposits, receives withdrawals and pays for the service." />

- **The connected account never submits a spend by default.** Submitting from it would publicly link it to the spend. It could submit only through an explicit override, which needs a wallet API that no extension offers yet.
- **The relayer submits plain spends.** When it cannot, the fallback is another relayer and then the vault's own submitter account. Each fallback submission is linkable, so the wallet asks first.
- **Nothing links a session to a spend.** No login session, cookie or wallet credential reaches the prover server, the relayer or the ticket redeemer.

## Expiry and submission

Every spend carries a public `valid_until`. The pool accepts it only up to that block, and only if `valid_until` sits on a grid and is not too far ahead:
- on Sepolia the window `E` is 1,500 blocks (about 42 minutes);
- the grid `Q` is 100 blocks.

A proved spend that nobody submits in time can never land later, which bounds how long anyone can withhold it.

The relayer answers each job with a transaction hash or a refusal. The wallet submits the same transaction itself only in two cases:
- the relayer refused the job;
- the deadline is within 40 blocks and no relayer transaction is pending.

So the relayer and the wallet never both land it.

## Account-bound notes (removed)

An earlier design made existing wallets co-sign every spend: a **bound note** needed the Templar key and a signature from one Starknet account, checked inside the proven execution. It protected notes when only the Templar backup leaked, but it cost privacy (the prover server learned which account made which spend), accepted only two account classes, and was the most complex code in the relation. ADR-0027 removed it:
- the client SDK and the prover server no longer create, plan or serve bound spends;
- pool V3's verifier moves to R0 V6, which has no account at all; bound notes made during the Sepolia tests become unspendable then.

For what has run, see [implementation status](/status#existing-wallets-r0-v5).
