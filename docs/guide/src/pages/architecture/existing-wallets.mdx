# Existing wallets

Templar offers two products on one pool:
- **Existing Starknet wallets** (Ready, Braavos) in a web app. Each spend needs a signature from the user's own account.
- **The Templar wallet**, whose own key authorizes spends.

Both settle the same kind of spend (R0 V5) in the same pool (pool V3), so both share one anonymity set. On chain, a spend authorized by a Ready or Braavos account looks exactly like one authorized by a Templar key.

## Account-bound notes

A note for an existing wallet is **bound** to one Starknet account. Its receiver hashes that account into the spending authority. Spending it needs two things:
- the wallet's Templar spending key, derived from a separate 21-word backup;
- a valid signature from the bound account.

A payer cannot tell a bound receiving address from an ordinary one, and any wallet can pay either. Neither half alone is enough:

| Leaked | Effect |
| --- | --- |
| The Templar backup or device store | Reveals that wallet's bound notes, amounts and spends. Moves nothing without the account's signature. |
| The account's signing key alone | Moves nothing: the notes also need the Templar spending key |
| Both | Everything, as with any wallet |

A bound wallet keeps value in bound notes: change, deposits and returns all go to receivers bound to the same account. It creates no policy notes, because a policy settlement involves no account signature.

- **The signature is checked where it counts.** The statement account calls the owner account's own `is_valid_signature` inside the execution that the large proof proves. A spend lands only if the account itself accepted the signature.
- **The message hides in-pool details.** It carries the pool and the plain exit fields (a withdrawal's recipient and amount), plus a salted binding. So a wallet vendor or guardian service can see what leaves the pool, but cannot match an in-pool transfer except by signing time.
- **Every signer the account accepts can authorize.** That includes the owner, a guardian, or session keys, so the list of launch account classes records each class's signers.

## What the prover server learns

For a bound spend, the prover server learns **which account made which spend**. It cannot move funds or change outputs. It can delay a spend until the spend expires, or refuse it, so it could censor chosen accounts. Label it accordingly: a trusted prover for identity.

That is still much less than a hosted prover that receives the witness: keys, amounts and recipients stay on the device. The Templar wallet removes the identity link as well: its own key authorizes, and the server learns nothing about the spender ([privacy & trust](/architecture/privacy)).

## Expiry and submission

Every V5 spend carries a public `valid_until`. The pool accepts it only up to that block, and only if `valid_until` sits on a grid and is not too far ahead:
- on Sepolia the window `E` is 1,500 blocks (about 42 minutes);
- the grid `Q` is 100 blocks.

A proved spend that nobody submits in time can never land later, which bounds how long anyone can withhold it.

The service's relayer submits every spend the server proves, from its own account, and answers each job with a transaction hash or a refusal. The wallet submits the same transaction itself only in two cases:
- the relayer refused the job;
- the deadline is within 40 blocks and no relayer transaction is pending.

So the relayer and the wallet never both land it. A bound account never submits its own spends, since that would link it to the spend on chain.

## Supported accounts

At launch, bound notes accept accounts whose class the wallet and the server have measured, with a Stark-key signer:

| Wallet | Account class | Notes |
| --- | --- | --- |
| Ready | Argent 0.5.0 | Without a guardian |
| Braavos | Braavos 1.2.0 | Stark signer |

Accounts with guardians, multisig or P-256 and passkey signers are refused at setup. For example, a Ready account with a guardian rejects owner-only signatures. Before creating a bound wallet, the web app checks the account's class and signers at one block, and the wallet signs a setup message that can never authorize a spend.

## What observers see

On chain, a bound spend and an ordinary one publish the same data. The gateway receives the large proof. Its public shape is the same for ordinary, Ready and Braavos spends: the header (proof version and circuit), and the circuit's fixed component sizes. The mode and the account differ only inside the proof's witness, so hiding them from the gateway rests on the large proof's zero knowledge.
