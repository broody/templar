# Proofs & verification

A zero-knowledge proof lets a holder demonstrate that a program accepted a private input without
revealing that input. Templar uses it to authorize one specific operation while keeping input
ownership, note amounts and membership paths private.

**Soundness** means an invalid claim should not verify. **Zero knowledge** means the proof should
not disclose private witness information beyond the public statement. Both depend on the proving
construction and on correct application checks. [Proving](/architecture/proving) describes how the
device and the wrapping server divide the work.

## What every spend proves

The compact R0 relation proves that:

- each spending secret derives the receiving identity committed into its input note;
- each input commitment belongs to the selected tree root;
- each nullifier is derived from the owner's nullifier key, the commitment and its leaf position,
  and the inputs are distinct;
- each output commitment matches its receiving identity, randomness, amount and chain/pool/asset
  context;
- every note of the spend uses one private asset, published only when value leaves the pool;
- a second input may be a zero-value dummy, whose membership is not checked;
- amounts are range-checked and conserved exactly for that asset;
- the public result binds the nullifiers, output commitments with their delivery digests, and
  withdrawal destinations and amounts.

Encryption happens in the wallet, outside the proof. The proof binds delivery digests but does not
prove correct encryption or receipt. The pool recomputes each digest from the published
ciphertext, and recipients verify decrypted openings before crediting notes.

The pool also checks that each nullifier is unused in current state: a valid membership proof is
not enough, because spent leaves remain in the tree.

## Binding the public result to the transaction

A proof's public output is small. The transaction additionally carries the asset on exit, nullifiers,
output commitments, ciphertexts, withdrawals and, where present, the execution intent or policy
fields. A **statement binding** ties them together: a hash over every public field, in a fixed
order with fixed counts and zero padding, so the encoding is unambiguous.

The client proof's outputs carry the whole public statement as field limbs. The bridge decodes and
range-checks it, rejects an asset published without a withdrawal or execution intent, and computes the
binding (`TMR0_BIND_V4` for R0, `TMP1_BIND_V1` for P1); the statement account emits it in its message.

The pool computes each delivery digest from the actual ciphertext bytes, recomputes the
binding from the transaction's data, and requires it to match the proven one. Changing a payload,
adding an output or redirecting a withdrawal changes the binding, and an old proof cannot be reused
for the altered operation. This is why encrypted publication is part of the protocol rather than an
optional off-chain message.

## The proving pipeline

The client proves R0 or P1 with a blinded stwo-circuits proof in an
arithmetic-only component profile (no lookup tables, so no multiplicities to leak). The wrapping
server runs a statement account whose bridge verifies that proof with the pinned circuit hash and
emits `[class, tag, chain, pool, binding]`. The server proves the virtual execution as a large
proof, through Starknet's large-proof flow. The account's virtual message is committed to by the
proof; it is not a real bridge withdrawal. The proof travels on the transaction, not as a Cairo argument. R0 and P1 each have their own bridge, statement account and account
tag, so a proof of one can never be accepted as the other.

Memory is the main engineering constraint on the server. A bounded-memory mode keeps polynomial
coefficients instead of expanded evaluations, rebuilds Merkle trees for openings and processes FRI
inputs in batches. It changes storage only: proofs are byte-identical. It brings the
large proof's peak from about 51 to about 28 GiB.

## Verification has three layers

| Layer | Question it answers |
| --- | --- |
| Starknet native verifier | Is the cryptographic proof valid for its claimed computation and output? |
| Verifier adapter | Is this the approved virtual OS and statement account, with the expected message for this pool, chain and spend, and a recent enough base block? |
| Pool | Is the root accepted, are the nullifiers unused, does the actual bundle match the binding, and do the external call, controller approval, token transfers and publication all succeed? |

The adapter pins the proof format, virtual OS program, statement account and class, the message
layout and count, and a maximum base-block age (4,096 blocks in the reference). A valid proof of an
unrelated program cannot authorize a spend.

The `IVerifier` interface's proof span is empty for these adapters because the real proof is
attached to the transaction; the adapter reads verified facts from the execution context. A valid
proof can still meet an expired root, a spent nullifier, an invalid withdrawal or a failed token
transfer: settlement requires every layer to accept the operation. Measurements and qualification
are on the [status page](/status).
