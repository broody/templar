# Return notes

A **return note** prepares a destination for funds whose amount will be known only after an external operation. A wallet can authorize a swap and receive its proceeds into its cloaked balance in the same transaction. The funded result is an ordinary note that can be sent or withdrawn through the usual ownership proof.

For example, a wallet holding ETH can convert part of it to USDC and then use those proceeds for a private payment. It prepares the receiving information before the swap, while the public market determines the actual output. Return notes require no controller.

The return destination is local to that execution. It has an opaque identifier, expected token, minimum amount, ownership commitment and encrypted recovery payload. It holds no balance and grants no spending authority before funding. Only the final funded commitment enters the append-only tree.

The wallet's proof binds the adapter, complete call data, input budget, expiry and every return destination. Changing a route, receiving destination or encrypted payload invalidates that authorization. Public execution enforces the minimum output against actual market state.

## Funding is checked by the pool

The pool checks that the adapter's returned identifiers and tokens match the authorized destinations. Each required return must appear exactly once in the authorized order and meet its minimum. The pool pulls the tokens and checks its actual balance increase before publishing the note.

The pool grants no external adapter allowance over its existing holdings. Funding, external execution, collection, private change and nullifier consumption share one transaction and a reentrancy lock. A failure in any return also reverts earlier effects within that transaction.

An adapter's return amount is a funding instruction, not evidence that the pool received money. Token compatibility and the wallet's choice of external protocol still matter.

## Recovery uses the actual amount

The wallet encrypts ownership and recovery information before it knows the output amount. Settlement publishes the actual amount and authenticates it together with that encrypted payload. The recipient decrypts locally, reconstructs the commitment using the settled amount, and checks the funded leaf before crediting the note.

Seed recovery and full viewing use the same history as ordinary payments, including the authenticated return amount. After recovery, the resulting note follows the ordinary ownership and nullifier rules. Users need no separate withdrawal secret or claim step.

## Adapter compatibility

Templar calls an adapter's `privacy_invoke` entry point. The adapter returns `OpenNoteDeposit` records containing an identifier, token and amount, and approves the caller to collect those funds. This is the upstream adapter interface.

Templar's internal type is **`ReturnNote`**. It describes a destination awaiting funding within an execution. The boundary type **`OpenNoteDeposit`** retains its upstream name and encoding. Adapters do not need to understand Templar's Merkle tree or receiving-key construction.

The execution model has one prefunded call and bounded return destinations. Private change and funded returns share the total note-output budget. A returned asset can differ from the input token: input conservation and incoming funding are checked separately in their respective token units. There is no persistent empty note, partial funding or asynchronous claim in this model.

## Privacy boundary

The swap or other external operation remains public. Its call, tokens, amounts, timing and return deposit are linked onchain. The intended protection concerns the earlier private input's membership and the receiving identity, subject to the usual proof, encryption and anonymity assumptions.

Transaction submission, gas funding, RPC queries and amount/timing correlation retain their own privacy implications. A return note does not turn a public AMM into a private exchange.
