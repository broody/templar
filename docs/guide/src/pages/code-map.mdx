# Code map

Paths are relative to the repository root. They identify source responsibilities rather than
installation steps; the repository README has the commands to build and test them. The primary
packages under `packages/` have not yet adopted these formats.

## Client side

| Path | Responsibility | Read alongside |

| `bench/m31-private-wrapper/client-port/src/payment.rs` | The R0 relation: note, tree and nullifier hashing, native reference, circuit (ordinary spends, open-note intent, identity handle) | [Proofs & verification](/architecture/proofs) |
| `bench/m31-private-wrapper/client-port/src/payment4.rs` | R0 V4: a private asset published only on exit, a dummy input, always two outputs; `bridge_checks` mirrors the bridge | [Assets & hidden transfers](/architecture/assets) |

## Server side

| Path | Responsibility |
| --- | --- |
| `bench/m31-private-wrapper/client-port/cairo-r0/`, `cairo-r4/`, `cairo-p1/` | Bridges (verify a client proof against the pinned circuit, decode and range-check the statement, compute the binding) and statement accounts (emit the message) for R0 V3, R0 V4 and P1 |
| `bench/m31-private-wrapper/client-port/build_bridge_arith.py`, `validate_bridge_r0.py`, `validate_bridge_r4.py`, `validate_bridge_p1.py` | Build a bridge from a trusted circuit manifest; validate it on a real proof against altered statements |
| `bench/m31-private-wrapper/client-port/capture_os.py` | Run a statement account in the virtual OS and check its exact message |
| `bench/m31-private-wrapper/proof2-large/` | Large-proof wrapping, the bounded-memory server build (`bounded/`) and a per-stage memory profiler |

## Earlier references

The first, full client-side reference (a felt252 note format proved on the device as a small proof) is
archived with its Sepolia evidence in `bench/push-e2e/`, `bench/controlled-push-e2e/`,
`bench/return-note-e2e/` and `bench/bounded-memory/`. It is no longer maintained; a device-side
path is [future work](/architecture/proving#future-a-faster-device-side-path). The
`bench/m31-private-wrapper/qm31-opcode/` experiment measures what native M31 arithmetic would buy it.

`docs/push-payment-spec.md` (receiving, delivery and recovery), `docs/open-note-spec.md` and

## A useful reading order

Start with `payment.rs` for the note and spend rules, read the R0
bridge next to it to see how the public statement is decoded and bound, then `pool.cairo` and
`adapter.cairo` for settlement, and `policy_e2e.py` for a complete run.

A check made only by a client is not a pool invariant. A valid proof matters only if the adapter
selects the intended statement and the pool applies exactly its bound operation. A recovery result
also depends on complete encrypted history and a trustworthy canonical checkpoint.
