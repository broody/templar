# Implementation status

<div className="guide-eyebrow">Snapshot / 21 September 2026</div>

Push payments are the accepted architecture for the initial product. Separate ordinary and controlled push-payment pools have completed offline receipt, full viewing, seed recovery, recovered-note spending, and withdrawals on Starknet Sepolia 0.14.4 using real native PROOF1 verification. The primary packages and a production wallet are not yet integrated with this format.

The reference is an unaudited construction. Its key derivation, address and backup formats, viewing exports, and delivery representation require independent review before a production format is frozen.

| Offline push payments | Alice and Carol independently send 600 and 250 to Bob's same receiving address while his wallet is offline |
| Full viewing | A separate process with viewing material finds 850 without spending authority |

The integration records **four successful native spends, two deposits, and three adversarial reverted transactions**. Its local validation records **59 Python tests and 59 Cairo tests**. Local pool guards include mock verifier fixtures; the separate live transactions establish actual native-proof integration.

The experiment used a synthetic faucet token, distinct note keys for the participants, and one public relayer account. It exercised programmatic wallet behavior, not a released user interface. Final private balances total 1,150 and match the remaining pool tokens.

## Controlled payment validation

The distinct `TEMPLAR_CONTROL_POC1` experiment demonstrates **owner proof plus real controller signature**. Alice sends offline Bob 600 controlled units. A full viewer finds that receipt and a fresh process restores Bob from seed. With approval, Bob pays Dave 500, keeps 60, and withdraws 40. After deleting his recovered cache, a second restoration finds the 60 and withdraws it with another approval. A separate ordinary payment succeeds without a controller signature.

This run records **four successful native spends, two deposits, five adversarial on-chain rejections, and two rejected native statement executions**. Six distinct proofs verify locally, including the new proofs used for the expiry and changed-destination tests. Local validation passes **55 Python tests and 68 Cairo tests**; mock-verifier guard tests and real native transactions remain distinct evidence.

| --- | --- |

| Signature from another key | On-chain rejection; state and balances unchanged |
| Valid signature over an expired request | On-chain rejection |

Final wallet checks reconcile 1,200 unspent units to pool tokens: Alice 400 controlled, Dave 500 controlled plus 100 ordinary, and Carol 200 ordinary. Bob has withdrawn 100. Restored and viewed notes preserve their controller and policy. Network gas is charged for reverted transactions even though pool state and synthetic token transfers revert.

The controller is an immutable-key Stark ECDSA fixture with a scoped off-chain policy, not a full application policy service. It has no escape, key rotation or revocation mechanism. Controller refusal can freeze value. [Policy notes](/architecture/policy-notes) (ADR-0025) supersede this design; this evidence is kept as history.

## Return-note integration

`ReturnNote` prepares a transaction-local destination for externally funded proceeds. The reference in `bench/return-note-e2e/` uses the upstream `privacy_invoke` / `OpenNoteDeposit` interface, then creates ordinary funded tree notes. Adapter source is imported unchanged at a pinned revision.

Local checks pass **11 Python tests and 24 Cairo tests**, including ownership-statement vectors, malformed/missing/duplicate returns, minimum output, reentrancy, funding rollback, repeated return tokens, and a same-token refund. The unchanged upstream Vesu adapter passes supply and redemption against its mock vault. This does not qualify live Vesu, borrowing or production tokens.

**Sepolia passed on 21 September 2026.** The unchanged upstream Ekubo adapter converted 1,000 synthetic input units into 999 output units using deployed Ekubo contracts. Fresh seed restoration and full viewing recovered the return. The restored wallet paid Bob 900 privately, and Bob's fresh wallet recovered that payment. Both native proofs verified locally and settled onchain: [swap](https://sepolia.voyager.online/tx/0x40506b834bcfaad59274f242d26d9717597358ba8fa76244978a0d01973172) and [recovered-note payment](https://sepolia.voyager.online/tx/0x58bb385bd744e6ac1960f6f43a40b6ce08208545954c1d80bbec8402efcbbda).

Six adversarial transactions were rejected without changing pool or token state: standalone withdrawal, stripped intent with reused proof, redirected return, changed call, changed return identifier and replay. Native execution also rejected a tampered intent. Final holdings reconcile to Alice's 4,000 A plus 99 B and Bob's 900 B; the adapter retains no tokens.

## Open notes on the compact path

The compact client proof (R0 V3) binds a public execution intent and an optional identity handle. The M31 pool's `apply_spend_with_invoke` settles `INVOKE` (Ekubo- and Vesu-style anonymizers) and `COMPUTE` (upstream's shadow-account anonymizer, restricted to owner-allowed classes).

**Local end to end with real proofs:**

| Stage | Result |
| --- | --- |
| Client proof | 2.0 s, 0.31 GiB |
| Bridge | 19/19 cases, 1.99M steps |
| Virtual OS | 3.34M steps, exact message |
| PROOF2 | 119.6 s, 253,430 bytes, 52.1 GiB |
| Settlement | passes in snforge with the real proof facts |

One output plus one funded open note costs 62.3M L2 gas in the pool call.

**Review.** Three independent reviews (relation math, statement binding, pool contract) found that a public nonce on the public identity handle let anyone enumerate a user's shadow accounts. The nonce is now fixed at zero, and accounts are separated by a private scope. The pool rejects malformed destinations before any external effect, and `COMPUTE` targets must be allowed classes. 32 adversarial open-note tests pass: 12 from the contract review and 20 new, including the target allowlist. A re-review of the fixes is pending.

**Sepolia (2026-09-24):**
- The deposits are on chain.
- The proof-carrying swap of 300 A through upstream's unchanged Ekubo anonymizer and the live Ekubo router, into an open note of 299 B, succeeds when the exact signed transaction is simulated against live state: 150.3M L2 gas, 3.80 STRK.
- The gateway still rejects PROOF2 (`PROOF_VERSION_NOT_ALLOWED`).
- Evidence is in `bench/m31-sepolia/results/v3-open-note/`.

A shadow-account end to end with upstream's anonymizer has not been run.

## Policy notes

The design (ADR-0025, `docs/policy-note-spec.md`) was reviewed independently before implementation: three revisions, ending with GO from both the math and protocol reviews. The implementation adds the P1 relation, its bridge and account, `apply_policy_spend`, the reference escrow and the wallet's seed-recoverable backup.

**Tests:**
- P1 relation: 7 tests, covering the native reference, tampered witnesses, the refund-slot rules and finalization.
- P1 bridge on a real proof: 32/32 cases, including every altered statement field and an R0 proof.
- Pool: 181 tests, of which 79 are policy tests. They cover decoy notes on another escrow, unset approvals, controller revert, re-entry and wrong return, rollback of a failed callback, and replay.

**Local end to end with real proofs** (`bench/m31-pool/policy_e2e.py`):
1. A depositor creates two escrow notes by deposit.
2. An executor holding only one note's opening proves the arbiter-approved release.
3. The depositor recovers the other note from the seed alone and proves its refund after the deadline.
4. Both settle through the P1 PROOF2 adapter, and the pool's tree ends at the root the beneficiary's wallet computed.
5. The beneficiary finds its notes by trial decryption and proves an ordinary spend of them.

| | Release | Refund |
| --- | ---: | ---: |
| Client proof | 5.3 s, 0.31 GiB | 1.9 s, 0.30 GiB |
| Bridge | 2.02M steps | 1.96M steps |
| Virtual OS | 3.41M steps | 3.33M steps |
| PROOF2 | 111.0 s, 50.9 GiB | 110.8 s, 51.7 GiB |
| `apply_policy_spend` | 52.4M L2 gas | 51.5M L2 gas |

The implementation review found no blocking issue in the relation or the contracts; its wallet and defense-in-depth findings are addressed, and both reviewers' tests (33 contract and 11 malicious-witness) are in the repository. The wallet's derivations and encodings are pinned by known-answer vectors.

**Still open:**
- a real-proof split settlement;
- private creation through an ordinary output, end to end;
- Sepolia, which is blocked on PROOF2 acceptance at the gateway;
- a production wallet key scheme: the end to end uses fixture spending and incoming keys.

The experiment replays local fixtures and sends no new chain transactions.
It leaves the live 4/4/2 limit unchanged. Its 4 GiB cap test still runs out of

and browser qualification remain open; the cap excludes the RPC cache, benchmark

Cairo and rejected nine altered inputs. This establishes a serialization and
verifier bridge, not a payment prover or a completed native PROOF1 round trip.

Evidence and reproduction are in `bench/wasm-membership/`.

### Proposed compact-client architecture

**ADR-0024 is Proposed; local Cairo/PROOF1 proving remains the accepted
architecture.** The proposal evaluates a compact private proof on the client
and a service that verifies and wraps it into PROOF1. The service receives
public inputs and proof bytes; private payment validity must be enforced in
the client proof, with the full verification enforced by the outer proof.

The custom M31 membership experiment in `bench/m31-private-e2e/` demonstrates
a private leaf preimage and one depth-32 path. Three native proofs take
**1.17–1.20 seconds at 63–64 MiB peak RSS**. Three proofs in a Chrome WASM worker
take **1.89–2.12 seconds**, with linear memory stable at **79.94 MiB**. All six
pass a separate native verifier given only public input and proof; the browser
also accepts a native artifact. Proofs are roughly 3.4 MiB. Whole-browser
memory is additional: sampled totals peak near 1.08 GiB summed RSS and
466.5 MiB summed PSS on the development workstation.

Protocol/source review and the independent math/PCS challenge reviews support
this research milestone under their explicit random-oracle and randomness
assumptions. The numerical bound concerns single-proof knowledge error in the
classical programmable random-oracle model; unrestricted adaptive multi-proof
service composition remains open. This is not a production audit or a full
payment benchmark.

A separately versioned Blake candidate preserves the membership relation and
M31 application tree. Native proofs take **0.98–1.03 seconds at 52.7–54.5 MiB
peak RSS**; Chrome WASM proofs take **1.71–1.92 seconds at 63.25 MiB linear-memory
high water**. Proofs are approximately 2 MB. Native/browser cross-checks and
version/rejection controls pass; evidence is in `bench/m31-private-blake/`.

A public hash-work component produces genuine PROOF1 accepted by the original
verifier, but the complete private membership verifier has not been wrapped.
A specialized server hash circuit verifies in Cairo; checked M31 inversion
reduces its verification steps by **15.37%**. Actual OS work still requires
log22 trace components. A larger experimental configuration exhausts a
**96 GiB server cap** before producing a proof and requires different trusted
verifier parameters. These are server capacity findings; the compact-client
measurements above do not include wrapping. See `bench/m31-private-wrapper/`.

Adoption requires reviewed complete ordinary payment constraints, measured
server wrapping, actual Sepolia payment acceptance, and an explicit hash/note
format and service-availability decision. The proposal is recorded in
`docs/adr/0024-compact-client-proofs-and-server-wrapping.md`; source identities,
measurements and limitations are in `bench/m31-private-e2e/results/README.md`.

## Spend capacity pathfinding

The funded reference currently permits **4 inputs, 4 outputs and 2 withdrawals**. This is an application cap, not a native-prover note-count ceiling. Separate synthetic native PROOF1 statements tested a 64/64/32 program ceiling with either fixed padding or explicitly counted active entries.

| Active inputs / outputs / withdrawals | Counted statement result | Prover request | Peak prover RSS |
| --- | --- | ---: | ---: |
| 8 / 8 / 4 | Verified | 19.12 s | 14.27 GiB |
| 16 / 16 / 8 | Verified | 19.85 s | 15.38 GiB |
| 32 / 2 / 0 | Exceeded 16 GiB cgroup cap | — | — |
| 1 / 32 / 0 | Verified | 20.21 s | 14.45 GiB |

Padding to a larger ceiling raised the small-payment case to 15.27 GiB; processing counted active entries kept it at 13.62 GiB in this sweep. Input membership paths, output publication and public withdrawals have different costs, so their caps should be qualified independently.

These are single synthetic-statement runs under four cores and a 16 GiB process cap, with local proof and public-message verification. They do not establish funded larger-bundle settlement, controller-service capacity, mainnet fees or physical 16 GiB desktop suitability. The successful 16/16/8 case leaves very little room for other software on a machine with 16 GiB total RAM.

The live pool remains at 4/4/2. Counted encoding and an 8/8/4 integration candidate need a versioned statement/pool/controller update, actual settlement and recovery tests, repeated worst-case measurements and device qualification. Benchmark sources and public evidence are in `bench/native-shapes/` and `bench/native-counted-shapes/`.

## Recovery and synchronization

The live scanner pins one accepted block and requires agreement between two RPC providers on the block, pool class, root, count, indexed commitments/delivery digests, and candidate-nullifier flags. It rebuilds the root, verifies payloads, and rechecks canonical block identity after the scan.

Both providers are trusted for state authenticity. This is not consensus verification or a state-proof light client. Colluding providers could lie. Candidate-nullifier queries reveal wallet access patterns to the providers, so private spent-status synchronization still needs work.

Five fresh watch/restore scans over only 6–8 notes took approximately **16.5–31.5 seconds**, despite carrying only 1,824–2,432 ciphertext bytes. Per-position RPC reads dominate this small reference implementation. These results do not establish scalable history synchronization.

Missing payloads produce incomplete results rather than complete zero balances. Corruption and omission drills use real downloaded history. Reorg handling is covered by fixtures, not forced Sepolia reorganizations. Balances are explicitly as of the checkpoint; L2 acceptance is not irreversible L1 finality.

## Current configuration boundary

The adapter pins PROOF1, the V1 virtual OS, statement address/class, chain/pool, and the public message layout. Its experimental maximum proof age is **4,096 blocks**, separate from the **256-root** pool history.

The controlled-push reference supports ordinary and controlled notes. The original ordinary-only POC2 pool retains its separate protocol and evidence; formats are never reinterpreted. The pool owner can change verifier and fee configuration, so the deployed prototype is not immutable.

Submission uses sncast signing and the official Sepolia gateway for proof-bearing transactions, with explicit fee bounds. Proof-aware estimation and proof preservation through the intended wallet/RPC path remain unqualified.
