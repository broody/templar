# PROOF1 proving memory

An isolated, reproducible port of stage-local allocations to the exact native V1
pipeline used by the Sepolia references. [Findings and next experiment](../../docs/prover-memory-review.md).
**Result:** fresh-process release proving for synthetic 8/8/4 used 11.18–11.28
GiB, down from 14.37 GiB stock. The 8 GiB target is not met; a long-lived release
process exceeded a 12 GiB cap on its third proof. Across the experiment, 38
proof runs passed independent verification and 114 proof/fact mutations rejected.

The active priority is reducing memory while preserving a future browser/WASM
path; this is not a WASM implementation or a production hardware qualification.

`TEMPLAR_LOW_MEMORY=1` selects the new entry point in the experimental service;
`0` or absence preserves stock caching. Invalid values fail startup. Optional
`TEMPLAR_CAIRO_COEFFICIENTS=0` selects an existing upstream recomputation option
in staged mode, without changing cryptographic parameters. It was slower for
little memory benefit; keep the default enabled. One request at a time is part
of these memory limits. The API does not impose a global concurrency limit.
The uninstrumented release service exceeded 12 GiB on its third consecutive
8/8/4 proof. The portable optimization is useful, but a long-lived service is
not qualified at that cap. `--native-allocator` tests glibc arena/trim settings
separately; those settings are not a WASM optimization.

## Reproduce on this workspace

Prerequisites are the original pinned source builds and the private runtime
fixtures generated by `controlled-push-e2e`, `native-counted-shapes`, and
`return-note-e2e`. They are not copied into this public benchmark archive.
`setup.py --help` exposes source/toolchain path overrides. The snapshots pin
sequencer `e6b6fd2e9932909107833579e5b6efd6c75fa0af` and proving-utils
`3035dd00421daa541894297bd754db6e2787807b`. Rust nightly-2026-01-15,
release and `-Ctarget-cpu=native` reproduce this host; that CPU setting is not a
portable shipping baseline.

```sh
python3 bench/prover-memory/setup.py
python3 bench/prover-memory/prepare.py
python3 bench/prover-memory/build.py --profile-allocations
python3 bench/prover-memory/build.py
python3 bench/prover-memory/test_harness.py
python3 bench/prover-memory/run.py --variant stock --fixture ordinary --cap 16 --name fresh-stock
python3 bench/prover-memory/run.py --variant staged-release --fixture ordinary --cap 12 --requests 3 --name fresh-staged --block BLOCK_FROM_FRESH_STOCK
python3 bench/prover-memory/analyze.py
python3 bench/prover-memory/validate_archive.py
```

Use fresh run names: existing measurements are never overwritten. Do not run
builds and proving benchmarks concurrently. `sweep.py` records the exploratory
matrix used here; its original names and block are intentionally preserved, so
use new names/blocks for another session. Individual runs are the supported
replay interface. `run.py --help` lists fixtures and options.

Source/build copies live in `target/prover-memory`, leaving Cargo's caches and
the accepted stock prover intact. `bin/profiled-prover` includes native allocator
counters; `bin/low-memory-prover` omits them. Portable proving changes are separate
from native diagnostic and service modules. `prepare.py` regenerates patches
from pinned original sources and the new entry point from the exact stock
proof-building function; `build.py` records source and binary hashes.

The public-read proxy caches block-pinned state responses for deterministic
comparisons after upstream storage-proof pruning. It accepts only read methods,
rejects proving/call/submission methods, never caches RPC errors, and does not
cache `latest`/`pending` state. The private proving request goes only to the local
prover. The cache remains in `target/`; no spending keys, witness files or signed
transactions are exported. This proxy is benchmark infrastructure, not the wallet
indexer or a new trust model.

## Interpreting measurements

- Four fixed physical i9-10980XE cores on a larger host, hard cgroup memory cap,
  `MemorySwapMax=0`, one proof at a time. The one-thread comparison still allows
  four CPUs but limits Rayon/Tokio workers to one each.
- RSS and cgroup peak include prover startup. Rust allocation counters count
  requested live sizes, not native allocator overhead or C-library allocations.
- The native verifier and Python harness run separately and are excluded from
  the prover cap. A wallet and OS/browser headroom have not been qualified.
- Proving time includes bootloader adaptation and both proof stages. Staged
  precomputation happens per request; cached-mode precomputation is in startup.
  Request time also includes virtual OS execution and RPC/cache latency. Compare
  those phases separately: warmed cached reads make requests much faster without
  changing proof computation. Profiling also adds overhead; use release runs
  when comparing uninstrumented latency.
- Repeated requests in one process exercise allocation reuse/retention. Fixed
  witness/block inputs produce identical proofs; they are not independent random
  payment fixtures or a broad performance distribution.
- Ordinary/controlled/return cases reuse witnesses from previously funded flows;
  8/8/4 is synthetic. None of these memory runs submits a transaction.
- Early `return-staged-repeat` and `invalid-intent-staged` runs have no process
  RSS measurement because a renamed binary bypassed the initial sampler. Their
  cgroup and allocation counters remain valid. The sampler now matches the
  executable path; later release runs provide RSS measurements for each workload.
- Failed 8/10 GiB cases retain OOM evidence. A separate early cache-toggle attempt
  failed on RPC storage-proof pruning before proving; it is not a memory result.
- Passing the unchanged verifier plus three mutation rejection checks is
  regression evidence. It does not replace cryptographic review, a newly built
  prover's live acceptance test, or production integration.
